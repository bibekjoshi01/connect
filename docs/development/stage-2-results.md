# Stage 2 backend implementation

The reviewer approved the backend design on 2026-11-18, then requested that the
app be developed and run afterward. This increment implements that backend
scope. It does not claim an Android login flow or completion of native Stage 2
compatibility testing. The approval record and limitations are in [stage-2.md](stage-2.md).

## Available behavior

The [versioned contract](../../contracts/rest/accounts-v1.openapi.yaml) defines:

- Registration options, finish and proof: validate a username, verify registration,
  then require a fresh standard assertion before creating any account/device/session.
  Finish returns 202/assertion options; proof returns 201/session and device handle.
- Authentication options and finish: look up a random device handle, verify the
  enrolled credential, consume the ceremony, and rotate the session atomically.
- `GET /v1/me`: return the authenticated account's ID, username and permanent Call ID.
- `DELETE /v1/sessions/current`: revoke only the current session.

There is no password, email/SIM requirement, public directory, refresh token,
recovery, transfer, media engine dependency or authentication bypass. Sessions
expire after 15 minutes. A lost device credential, enrollment response or local
handle can strand an account. Keep device handles private and sessions in memory
when implementing the app.

`internal/accounts` owns the repository interface, WebAuthn policy, HTTP routes
and source limiter. `internal/accounts/postgres` owns the adapter. Account rows
serialize credential updates, rotation and logout; the active-device pointer is
the sole device authority. A deferred composite foreign key prevents a pointer
to another account's device. Read-only profile access checks PostgreSQL on every
request. Requests already authorized before revocation commits may be in flight.

Migration 2 creates account, device, ceremony and session tables. Its down
migration refuses any nonempty identity table. Migration 3 adds pending proof
state and revokes earlier sessions. Stop the API, explicitly run
`make backend-migrate` to reach version 3, then restart it. Existing credentials
can log in normally. Migrations 1 and 2 remain unchanged, and API startup never
applies migrations automatically. Downgrading with identity/ceremony data is refused.

## Authentication configuration and HTTPS

Default startup is still operational-only loopback HTTP. Account routes are not
registered until authentication configuration is supplied. This avoids inventing
an RP/domain or accepting an unreviewed Android signing certificate.

Set the following through the process environment or ignored local `.env`:

- `AUTH_RP_ID`: your reviewed RP domain, without scheme, path or port.
- `AUTH_RP_ORIGINS`: up to eight comma-separated exact HTTPS origins under that
  RP domain; no wildcard, user information, URL path or whitespace.
- `AUTH_ANDROID_ORIGINS`: optional exact `android:apk-key-hash:` origins with
  canonical unpadded base64url SHA-256 signing-certificate hashes, at most eight.
  Keep empty until native configuration has been reviewed.
- `API_TLS_CERT_FILE` and `API_TLS_KEY_FILE`: readable server certificate/key
  paths. Both are required when account routes are enabled. TLS is also available
  for operational-only mode. Keep private keys in ignored local files.
- `API_LISTEN_ADDR`: default `127.0.0.1:8080`; choose an appropriate loopback port
  for local HTTPS. The same listener serves operational and account routes.

Partial/invalid configuration fails startup. Account routes reject plaintext
requests independently of the listener; they never trust forwarded headers for
HTTPS or source identity. The client must verify the certificate and hostname.
Never use `curl -k`, disable certificate validation, or accept wildcard origins.
No reverse proxy, domain hosting or production ingress was provisioned.

The integration suite uses the reserved `connect.test` RP and HTTPS origin only
inside synthetic backend fixtures. These are not an Android association or a
production configuration. Test HTTPS certificates are generated by Go's test
server and trusted explicitly by its client, without disabling verification.

## Limits and operational behavior

Requests have a 32 KiB JSON limit, duplicate-key rejection, strict envelope and
credential-field decoding, and at most 32 JSON nesting levels. Database operations
have a two-second deadline. Eight verification operations may run per process;
excess work is rejected. Ceremonies expire after two minutes and accept at most
three verification failures.

PostgreSQL serializes ceremony admission across API instances: at most 1,000
stored ceremonies and three pending authentication ceremonies per device.
Admission first removes expired/consumed/exhausted rows in a bounded batch. A
minute-based cleanup worker removes up to 1,000 stale ceremonies and 1,000
expired/revoked sessions per sweep. Cleanup is best effort during dependency
failure; a public-service retention/throughput review remains necessary.

The source limiter allows five registration starts, twenty authentication starts,
and twenty finish attempts per minute per socket peer per process. It retains
at most 10,000 sources and evicts ten-minute-idle entries. Forwarded headers cannot
change the source. This is a local development safeguard, not distributed abuse
protection sufficient for public signup.

Only SHA-256 session-token and authentication-handle digests are stored. The
verifier's credential record and ceremony context contain no device private key.
Errors and existing operational metrics disclose no credential/driver details;
account request bodies and identifiers are not logged. Responses use `no-store`.

## Dependency review

`github.com/go-webauthn/webauthn` v0.18.2 and its resolved graph are pinned in
`backend/go.mod` and `go.sum`. The QA correction updates the pinned toolchain
to Go 1.26.11 for GO-2026-6859; dependency versions remain unchanged. The library verifies standard challenges,
signatures, origins, RP IDs, user presence/verification and extension policy;
Connect restricts registration to ES256 and rejects backup flags and clone
warnings. Zero signature counters alone are allowed by the standard policy.

This uses nonidentifying attestation and trusts the OS/provider; it does not prove
hardware-backed storage or a physical device on every bearer-authenticated request.
The source review is not a claim of independent cryptographic audit.

## Validation

Executed locally on 2026-11-18; the following checks passed:

```bash
make backend-check backend-integration backend-security
```


- Go formatting/vet, race-enabled unit tests and both executable builds passed.
- Real PostgreSQL tests passed for fresh/idempotent/concurrent migrations,
  protected rollback, WebAuthn enrollment/assertions, profile, session rotation,
  logout, expiry, replay, wrong operation/origin/RP, invalid signatures, missing
  user presence/verification, backup flags and clone warnings.
- Concurrent enrollment, credential reuse and login-consumption tests passed;
  distinct login ceremonies rechecked the latest signature counter. Cross-account
  device pointers were rejected, and inactive devices lost access. Capacity,
  cleanup, source/verification limits and database failures were exercised.
- The public-key-only enrollment regression is covered: registration creates
  pending assertion options only. No account/device/session exists before proof;
  an incorrect key/signature, original challenge, wrong operation/origin/RP,
  missing verification, expiry or exhausted failure budget cannot enroll.
- Legacy-session upgrade revocation and continued credential login are tested.
- The built API started with an explicitly trusted temporary TLS certificate,
  became ready, served registration options and shut down cleanly on SIGTERM.
  Lifecycle/transport redaction checks passed.
- `go mod verify` passed. The account OpenAPI parsed, its seven operation IDs were
  unique, and every local schema reference resolved. Documentation links/code
  fences and local Python-helper syntax checks passed. This was a structural
  contract check, not validation by a full OpenAPI validator.

The pinned govulncheck v1.10.0 scan runs through `make backend-security` and CI.
It reports no reachable known vulnerabilities under Go 1.26.11. A module-only
OpenPGP advisory remains in a transitive module, but this code imports/calls no
OpenPGP package; this result is not a claim that every module is advisory-free.

Flutter/Android checks were not rerun: no mobile source changed, and the previous
Flutter SDK is missing. There is no new APK or physical-device result. Public
security/load testing and deployment were not performed. Manual checkboxes remain
unchecked; automated fixtures are not a substitute for phone compatibility.

The integration suite uses the existing isolated `connect_stage1_test` database
name for both stages. After the component separation, its Compose fixture lives
in `backend/tests/integration/` and generates its own temporary credentials; a
root development `.env` is no longer required. It exercises real PostgreSQL, the actual WebAuthn verifier
and a synthetic ES256 authenticator over verified HTTPS. Its temporary keys and
responses remain in test memory. The dedicated Compose stack is removed after
the run; development data is not reset.

See [manual-testing.md](manual-testing.md) for the human review checklist.
